# Звіт до лабораторної роботи № 7

## 1. Тема, номер і варіант

- Спільна операція: `room_need()`; підсумок: завантаження аудиторій

| До (лабораторна № 6) | Після (лабораторна № 7) |
|----------------------|-------------------------|
| `dict[str, object]` (`LessonRecord` як `TypedDict`) | екземпляр класу `Lesson` |

лабораторної № 6 (`kzp_lab06`) залишено для порівняння звітів.

## 3. Модель

Клас `Lesson` (`src/kzp_lab07/models.py`):

- `__init__(subject, teacher, day, period, room)` присвоює значення через
  властивості, тож кожне проходить перевірку;
- `@property` із setter для `subject`, `teacher`, `day` (непорожній текст,
  пробіли обрізаються) та `period`, `room` (ціле число більше 0, `bool`
  відхиляється);
- setter записує у внутрішнє поле (`_period`), а не в себе, тому рекурсії немає;
- хибне значення викликає `ValueError` і не змінює попередній стан;
- `__str__` — «Фізика (Бойко А. А., Вівторок, пара 2, ауд. 120)»;
- `__repr__` — `Lecture(subject='...', teacher='...', day='...', period=2,
  room=120)`, з назвою підтипу;
- `__eq__` порівнює тип і всі поля, для чужого типу повертає `NotImplemented`;
- `__lt__` і властивість `sort_key` задають порядок: пара, аудиторія, предмет;
- `__hash__ = None`, бо об'єкт змінюваний (є setter-и) і не може бути ключем
  словника.

## 4. Dataclass

```python
@dataclass(frozen=True)
class RoomLoad:
    room: int
    lessons: int
    need: int


@dataclass(frozen=True)
class ScheduleSummary:
    total: int
    day: str
    lessons: int
    teachers: tuple[tuple[str, int], ...]
    rooms: tuple[int, ...]
    bounds: tuple[int, int] | None
    room_loads: tuple[RoomLoad, ...]
```

`frozen=True` забороняє змінювати поля (`FrozenInstanceError`) і робить намір
незмінності явним; колекції всередині — кортежі. `ScheduleSummary` — простий
підсумок, де важливий набір полів, а не поведінка, тому `@dataclass` доречніший
за звичайний клас; `Lesson`, навпаки, має setter-и й підтипи, тож лишається
звичайним класом. `RoomLoad` описує завантаження однієї аудиторії.

## 5. Підтипи та протокол

| Підтип | `room_need()` | Пояснення |
|--------|---------------|-----------|
| `Lecture` | 2 | лекція займає аудиторію дві академічні години (одна пара) |
| `Practice` | 1 | практичне — одну годину |

Спільну поведінку описує протокол:

```python
class NeedsRoom(Protocol):
    @property
    def room(self) -> int: ...
    def room_need(self) -> int: ...
```

`analysis.room_loads` приймає `Sequence[NeedsRoom]` і підсумовує
`lesson.room_need()` за аудиторіями. Перевірок `isinstance` у `analysis` немає:
це качина типізація, новий підтип чи будь-який об'єкт з `room` і `room_need`
працюють без змін. Тест `test_analysis_works_with_any_object_matching_protocol`
перевіряє це на класі, що не успадковує `Lesson`.

## 8. Порівняння звітів

Один і той самий CSV обробляють обидві реалізації; `test_compat.py` доводить,
що звіт лабораторної № 7 починається зі звіту лабораторної № 6 (для днів
«Понеділок», «Вівторок», «Середа», «Четвер» і порожнього файла), а
повідомлення про п'ять видів хибних даних збігаються слово в слово.

Для `data/input.csv`, день «Понеділок»:

Лабораторна № 6:

```
Записів у файлі: 3
День: Понеділок
Занять у цей день: 1
Заняття за викладачами:
  Олексів М. В.: 1
Аудиторії: 101
Перша пара: 1
Остання пара: 1
```

Лабораторна № 7 — ті самі дев'ять рядків і додатковий блок:

```
Завантаження аудиторій:
  101: 1 зан., 1 год
```

Для «Вівторок» блок має вигляд `215: 1 зан., 2 год`: аудиторія 215 — лекція
(потреба 2 години). Єдина відмінність зовнішнього формату — додатковий блок
в кінці, який відповідає вимозі варіанта «підсумок — завантаження аудиторій».

## 12. Відповіді на контрольні питання

1. Клас — опис структури й поведінки, екземпляр — конкретний об'єкт зі своїм
   станом.
2. `__init__` ініціалізує екземпляр після створення; `self` — явне посилання
   на поточний екземпляр.
3. `@property` дає доступ до значення як до поля, але виконує метод, тож можна
   перевіряти інваріанти.
4. Якби setter писав у саму властивість, він викликав би себе рекурсивно, тому
   записує у внутрішнє поле `_value`.
5. `@dataclass` автоматично створює `__init__`, `__repr__`, `__eq__` та інші
   методи за описаними полями.
6. `frozen=True` забороняє змінювати поля після створення й робить
   незмінність явною.
7. `__str__` — зрозуміле подання для читача, `__repr__` — діагностичне для
   розробника.
8. Для несумісного типу `__eq__` має повертати `NotImplemented`, щоб Python
   міг спробувати симетричне порівняння.
9. `key` у `sorted` простіший, коли порядок залежить від контексту й не є
   сталою властивістю об'єкта.
10. `super()` звертається до наступної реалізації за MRO, зокрема для
    виклику ініціалізації базового класу.
11. MRO — порядок пошуку методів у класах; його треба враховувати при
    множинному спадкуванні, щоб знати, чия реалізація викликається.
12. Качина типізація: важливо, які методи має об'єкт, а не якого він класу.
13. `Protocol` описує потрібну поведінку, тож функція приймає будь-який
    об'єкт із цим інтерфейсом без спільного базового класу.
14. Перевірки кожного підтипу змушували б змінювати `analysis` для кожного
    нового підтипу; поліморфний виклик цього не потребує.
15. У `loader`, на межі входу, щоб `analysis` отримував лише коректні об'єкти.
16. Бо імпорт у тесті чи іншому модулі не повинен запускати програму, тому
    код запуску стоїть під `if __name__ == "__main__":`.
17. Setter відхиляє хибні значення, dataclass незмінний, рівність, підтипи
    дають різні результати, спільна функція працює через протокол.
18. pytest перевіряє поведінку, ruff — стиль і типові помилки, wheel — що
    пакет збирається й встановлюється.
19. Порожній вхід, один запис, дублікати, нуль і від'ємні числа, відсутній
    стовпець чи значення, не-UTF-8, відсутній файл.
20. Номер варіанта, класи й поля, підтипи та спільну операцію, приклад
    звіту, порівняння звітів, команди, коди завершення, результати pytest,
    ruff, wheel і CI.
